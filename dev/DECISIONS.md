### DEC-001: Default `threads = 1` in every function

- Date: 2026-10-02
- Status: accepted (brief §3.5)
- Context: The reference defaults to `threads = 2` in `SM_output()` for the logistic models, hard-codes 4 in logistic RE/CRE `confint()`, and defaults to 1 elsewhere. CRAN allows at most 2 cores in examples and tests.
- Decision: Every function defaults to `threads = 1`, and thread counts are never hard-coded. This is a computational setting rather than a Class B change, because results must agree across thread counts within Tier 1/2 tolerances.
- Alternatives considered: Keep each function's reference default. This was rejected because it's inconsistent, and the hard-coded 4 violates CRAN policy.
- Consequences: The fixture generator passes `threads = 1` explicitly. The migration guide notes the change.

### DEC-003: One formula grammar and a `provider` argument for every family

- Date: 2026-10-02
- Status: accepted with the Phase 0 gate (2026-10-02); open question M-6 may still change which legacy interfaces survive
- Context: The reference has three input formats; the provider is an `id()` term for FE models, a `(1 | id)` term for RE models, and a column name for CRE models, and FE formulas are parsed with regular expressions (D-18). Brief §5.5 asks Phase 0 to choose between a formula special and a dedicated argument.
- Decision: New fitting functions take `formula` (response and covariates only, parsed with `terms()` and `model.matrix()`), `data`, and `provider` (one string naming a column of `data`), identically for FE, RE, and CRE models. CRE models add `within_between`. The compatibility wrappers accept all three reference formats and translate them.
- Alternatives considered: A formula special such as `provider(id)`, parsed with `terms(specials = )`. Idiomatic, but it mixes the grouping structure into the covariate formula, and for RE models it would sit next to lme4's own syntax. Keeping the vector interface in the new API was also rejected: a data frame is a cheap requirement, and it keeps a single validation path.
- Consequences: Transformations, interactions, and factor levels with spaces work in every family (fixing D-18). lme4 formulas are generated by the adapter, in the reference's term order (K-50), so lme4 results stay identical.

### DEC-004: S3 class hierarchy

- Date: 2026-10-02
- Status: accepted with the Phase 0 gate (2026-10-02)
- Context: Brief §5.2 allows at most one intermediate class, only where it removes real duplication.
- Decision: `pprof_model` is the base class. The four lme4-backed models share the intermediate class `pprof_mixed` (adapter, variance components, conditional SDs, printing). Firth is `c("pprof_logistic_firth", "pprof_logistic_fe", "pprof_model")`, so it inherits the logistic FE inference as the reference does (D-12, pending M-2). The FE models have no intermediate class. Results have their own classes (`pprof_provider_tests`, `pprof_measures`, `pprof_profile`, `pprof_funnel`, and so on; NAMING.md §5).
- Alternatives considered: Flat classes with shared helpers only (more boilerplate methods); `pprof_logistic_cre` inheriting from `pprof_logistic_re` (would leave no room for `pprof_mixed`, and linear CRE differs from linear RE in its standard errors, K-69 versus K-70).
- Consequences: If M-2 is answered "no", Firth drops the intermediate class and declares its own capabilities.

### DEC-005: Compact model objects; covariate-dependent methods take `data`

- Date: 2026-10-02
- Status: accepted with the Phase 0 gate (2026-10-02)
- Context: Reference objects carry the whole processed data and character row names: about 15 times the size of what downstream methods need (ARCHITECTURE §D.1, B5). Brief §5.2 asks Phase 0 to decide whether to keep covariates for the methods that need them.
- Decision: Objects keep the compact per-observation vectors of ARCHITECTURE §D.1 (at most 24 bytes per observation for FE models, 32 for RE/CRE) and keep the design matrix, processed data, and lme4 fit only with `keep_data = TRUE`. The three methods that need covariates (standard provider score test, covariate LR and score tests) take `data`, rebuild the design with the stored `terms` and settings, and verify the rebuild against the stored linear predictor before computing; otherwise they raise `pprof_error_data_required`. Compatibility wrappers fit with `keep_data = TRUE`.
- Alternatives considered: Always keeping the design matrix (simpler, larger); recovering data from the call environment (fragile).
- Consequences: The verification step makes a mismatched `data` an error rather than a silent wrong answer.

### DEC-006: R/C++ boundary

- Date: 2026-10-02
- Status: accepted with the Phase 0 gate (2026-10-02)
- Context: Brief §5.6 requires measured evidence for what stays in C++.
- Decision: Keep in C++, rewritten as an Rcpp-free core with thin adapters: SerBIN, BAN, Firth, the variance block inverse, the standard score test, and direct-standardization expectations. Move linear FE to direct demeaning in R. Keep everything else in R. Evidence in ARCHITECTURE §F (B1 to B4).
- Alternatives considered: Porting the logistic engines to R (the ports exist and reproduce the path, but are 1.6–2.3× slower and allocate hundreds of megabytes per fit); a C++ linear FE (unnecessary once demeaning removes the O(Σn_i²) cost).
- Consequences: The linear FE change must pass the reference suite at Tier 1 (B2 shows 1.5e-14 agreement on beta).

### DEC-007: One information-block routine with caller-supplied weights

- Date: 2026-10-02
- Status: accepted with the Phase 0 gate (2026-10-02)
- Context: The block information computation exists in eight places (ARCHITECTURE §A.2), each with slightly different weight handling (K-13, K-20, K-31, K-66). Brief §5.6 requires one shared, tested routine.
- Decision: `src/core/information_blocks` computes the diagonal, cross, and β blocks and the Schur complement from weight vectors passed in by the caller (separately for the diagonal, cross, and β blocks where the reference differs). Each caller passes the weights the reference used.
- Alternatives considered: One routine with one weight convention, which would change results (Class B).
- Consequences: The differences between callers become visible parameters, each tested.

### DEC-008: Quiet by default in the new API

- Date: 2026-10-02
- Status: accepted with the Phase 0 gate (2026-10-02)
- Context: The reference's `message = TRUE` default prints per-iteration logs and screening notices; `linear_fe` and the RE fits print with no way to stop them (D-36). Brief §5.5 asks for one verbosity argument with no output when it is off.
- Decision: New functions take `verbose = FALSE`. Screening results and convergence diagnostics are stored in the object and shown by `print()`. Non-convergence and screening exclusions still raise classed warnings (`pprof_warning_not_converged`, `pprof_warning_screening`), which are not suppressed by `verbose = FALSE`. Compatibility wrappers keep the reference's messages.
- Alternatives considered: `verbose = TRUE` (noisy for a modeling function, unlike `lm` and `glm`).
- Consequences: A presentation change, recorded in the migration guide.

### DEC-010: `check_data()` reports instead of stopping

- Date: 2026-10-02
- Status: accepted with the Phase 0 gate (2026-10-02)
- Context: `data_check()` stops on any missing value while the fits delete incomplete rows (D-17), and reports only through messages.
- Decision: The new `check_data(formula, data, provider)` returns a `pprof_data_check` object (missingness by column and overall; zero and near-zero variance with the `caret` thresholds; pairwise correlations above 0.9; VIF ≥ 10) with a print method. The `data_check()` wrapper keeps the reference behavior.
- Alternatives considered: Keeping the stop (inconsistent with the fits).
- Consequences: Not a statistical change: no model result depends on it.

### DEC-011: `confint()` means covariate intervals

- Date: 2026-10-02
- Status: accepted with the Phase 0 gate (2026-10-02)
- Context: The reference's `confint()` returns provider-effect or standardized-measure intervals, unlike every other R model class.
- Decision: `confint.pprof_model()` returns covariate intervals with the family's rule. Provider-level intervals come from `provider_effects(interval = )` and `standardize_providers(interval = )`. Old classes keep the old meaning through the wrappers.
- Alternatives considered: Keeping the reference meaning (surprising to R users; mixes two estimands in one generic).
- Consequences: Listed in the migration guide.

### DEC-012: Result objects are validated lists with a table and named settings

- Date: 2026-10-02
- Status: accepted with the Phase 0 gate (2026-10-02)
- Context: Reference results are data frames or matrices with string attributes (`"provider size"`, `"model"`, `"description"`, `"confidence_level"`), which plots parse (D-33), and flags are factors with data-dependent levels (D-15).
- Decision: Every result object is a list with a `table` (base data frame keyed by `provider_id` or coefficient name, with the column names of NAMING.md §5) and named fields for the settings used, built by `new_*()` and checked by `validate_*()`. Flags are integers -1, 0, 1. `tidy()` returns the table as a tibble. Plots read only these fields.
- Alternatives considered: Data-frame subclasses with attributes (attributes are lost on subsetting).
- Consequences: Presentation change only; wrappers rebuild the old shapes.

### DEC-017: Pinned, isolated reference library

- Date: 2026-10-02
- Status: accepted with the Phase 1 gate (2026-10-02)
- Context: Brief §3.1 requires fixtures from the pinned reference in an isolated library, with lme4 and Matrix pinned.
- Decision: `dev/reference/setup_reference_library.R` builds `dev/reference/lib` (gitignored) with pprof 1.0.3 from the MD5-checked CRAN tarball, built from source against the pinned Rcpp, RcppArmadillo, and RcppParallel headers, and its whole dependency closure (131 packages) from the Posit Package Manager CRAN snapshot of 2026-10-01. The snapshot's `Deriv` requires R ≥ 4.5, so `Deriv` comes from the CRAN Archive: the newest archived version that builds on R 4.4.0, which is 4.2.0 (4.3.0 fails to compile because it calls `Rf_allocLang`, which R 4.4.0 lacks). `dev/reference/library-lock.json` records every package, version, and source. The generator runs fixtures in child sessions whose library path is only this library plus base R, under `LC_COLLATE=C`, the collation testthat 3e uses for tests, because provider order depends on collation (D-34), and under `OMP_THREAD_LIMIT=1`, so one thread runs even where the reference hard-codes more (D-21).
- Alternatives considered: A snapshot at the reference's release date (2026-02-10): historically closer, but the rewrite is developed and tested against current versions, and lme4 comparisons are only meaningful under the same versions. Using the user library: not isolated and not pinned.
- Consequences: On this machine every numerically relevant version in the reference library equals the user library's, so tests run in the same environment as the fixtures. Installing pprof 1.0.3 on R < 4.5 now depends on an archived package (through `olsrr` → `car` → `pbkrtest` → `doBy` → `Deriv`), which strengthens DEC-009 (remove `olsrr`).

### DEC-018: Fixture design

- Date: 2026-10-02
- Status: accepted with the Phase 1 gate (2026-10-02)
- Context: Brief §3.1 and §6; the plan's budget of at most 5 MB and about 60 s for shipped fixtures.
- Decision: Two fixture sets with the same format: core (`tests/testthat/fixtures/reference`, shipped, 234 cases, 3.7 MB) and full (`validation/fixtures/reference`, build-ignored, 32 cases, 6.8 MB, of which 6.1 MB is one 80,000-row dataset). One case runner (`tests/testthat/helper-reference-cases.R`) is used by the generator and the tests, so a case is executed and processed identically on both sides. Values are stored processed: vectors and data frames longer than 5,000 elements become signatures (counts, sums, extremes, a 25-point sample, an exact checksum); lme4 fits become their extracted components (fixef, ranef with conditional variances, VarCorr, theta, logLik, vcov, fitted, convergence messages); ggplot objects become their layers' data, compared by position. Intermediate quantities (brief §3.1) are the ones the reference returns: `data_include` with its screening columns, fitted values and linear predictors, the observed and expected tables of `SM_output()` (`OE`), variances, and variance components; provider sizes and event counts are not stored as separate fields, but `data_include` fixes them exactly. Iteration counts of logistic FE and Firth fits are parsed from the C++ log; for `message = FALSE` calls a probe with `message = TRUE` recovers the count and must reproduce the estimates bitwise. Generated datasets are stored with the fixtures. Slow cases are marked `heavy` and skip on CRAN.
- Alternatives considered: Full objects everywhere (the core set would exceed the budget several times over); a separate test-side runner (two implementations of "run a case" could drift); extracting further intermediates by re-running internal steps of the reference (new code computing quantities the reference does not expose, which would itself need validation).
- Consequences: The runner is part of the fixture definition: changing it can change fixtures and therefore needs the regeneration procedure (approval and a diff report). Two independent generations were identical. On 2026-10-02 the project lead approved a regeneration (at `0639e2b`) that adds six core cases closing the two ARCHITECTURE §G.2 grid gaps (a fit with an lme4 `control` object for each of the four RE and CRE functions; three seeds of one bootstrap configuration) and the `ref_expr()` marker; the diff reports in `dev/reference/diff-reports/20261002-grid-gaps-*.md` show the 234 earlier core cases, the 32 full cases, and every dataset identical, and the core set is now 240 cases and 3.9 MB. On 2026-10-04 the project lead approved R-1 with the Phase 5 plan: 55 core cases and 4 small derived datasets (generator at `8821723`; diff reports `dev/reference/diff-reports/20261004-phase5-grid-*.md`: the 248 earlier core cases, the 32 full cases, and every dataset identical; a second generation identical to the first); the core set is now 303 cases, 35 datasets, and 4.43 MB.

### DEC-019: Relative component of the root-finding tolerance

- Date: 2026-10-02
- Status: accepted; signed off by the project lead on 2026-10-02 (tolerances change only with sign-off, brief §3.4)
- Context: ARCHITECTURE §G.4 approved `tol_root` as atol 2.5e-4, rtol 0, applied to provider-effect limits, with measure limits compared "after propagating through the measure". Interval tables mix effect-scale values (gamma, scale about 1) with ratio and rate limits (rates in percent, scale up to 100).
- Decision: `tol_root` uses atol 2.5e-4 and rtol 2.5e-4 for every value of a root-based interval table, so that the absolute bound on the effect scale carries over to ratio and rate limits in proportion to their size, instead of a per-measure propagation.
- Alternatives considered: Per-measure propagation through the derivative of each measure (more code in the comparison layer, harder to audit); rtol 0 (would reject rate limits that differ only through the effect-scale root tolerance).
- Consequences: On this machine every interval matches bitwise (validation report), so the choice matters only across platforms. ARCHITECTURE §G.4 is updated to match.

### DEC-020: lme4-backed comparisons only under the pinned versions

- Date: 2026-10-02
- Status: accepted with the Phase 1 gate (2026-10-02)
- Context: Brief §3.1: for lme4-backed models the oracle is the pinned pprof plus pinned lme4 and Matrix; version sensitivity must be documented, not hidden by tolerances.
- Decision: Characterization tests of lme4-backed cases (tier `lme4`) run only when the installed lme4 and Matrix versions equal the manifest's; otherwise they skip with a message naming both sets of versions, and the validation report lists them as skipped.

### DEC-021: Partial-matching warnings in the reference harness

- Date: 2026-10-02
- Status: accepted with the Phase 1 gate (2026-10-02)
- Context: Brief §5.5 requires tests to run with partial-matching warnings enabled, and the project's test rules treat those warnings as failures, but the reference relies on two partial matches (D-08).
- Decision: The reference harness enables `warnPartialMatchDollar`, `warnPartialMatchArgs`, and `warnPartialMatchAttr` while it replays a case, allows exactly the two D-08 messages, and fails on any other partial match. The legacy tests (the reference's own suite, 30 `test_that()` blocks, unchanged from `5260838`) run without these options, because some of them call functions that contain the D-08 matches (for example `summary()` on a `linear_re` fit).
- Alternatives considered: Enabling the options globally (the legacy tests would report D-08 warnings on every run).
- Consequences: Each allowlist entry is removed once the code containing that match has been replaced: `obs` (`SM_output.logis_fe`, logistic RE and CRE `confint()`) and `data_includ` (`summary()` for `linear_re` and `linear_cre`).

### DEC-022: What the characterization tests compare

- Date: 2026-10-02
- Status: accepted with the Phase 1 gate (2026-10-02)
- Context: Brief §3.2: messages, warnings, and print formatting may change; numbers, flags, and inclusion may not.
- Decision: Tests compare the outcome type (value or error), every element of the processed value with the case's tolerance tier (structure, names, dimensions, and non-double values exactly; flags exactly except at the decision threshold), the iteration count exactly, and, where the reference needed a probe, that the probe reproduced the estimates. Messages, warnings, printed output, and error messages are stored in the fixtures for reference but not compared.
- Alternatives considered: Comparing messages too (would fail on every permitted wording change).
- Consequences: A Class A fix that turns a reference error into a result fails that case's test. Such fixes will need a per-case expectation that cites the register entry, added with the first such fix.

### DEC-023: Benchmark measurement and regression rule

- Date: 2026-10-02
- Status: accepted with the Phase 1 gate (2026-10-02)
- Context: Brief §3.6 sets a target of no regression worse than about 10% in time or memory. In a trial baseline with one timed run per call over 1 s, that run differed from the first run by up to 59%. With repeated runs, timings of some tasks are bimodal (some runs include an expensive garbage collection): 8 of the 47 measured tasks have a median of at least 0.05 s that is more than 10% above their fastest run, by up to 50%.
- Decision: Each task runs in a fresh process on the pinned reference library (`dev/bench/run_reference.R`), with at least 5 timed runs for calls under 10 s and 3 otherwise; the baseline records the median, fastest, and slowest run, R allocations (calls under 10 s), and peak process memory. A later run regresses in time when both its median and its fastest run are more than 10% slower than the baseline's and the median is at least 0.05 s slower; when only one of the two is more than 10% slower, the task is rerun before it counts either way. It regresses in memory when its peak is more than 10% and at least 50 MB higher. Comparisons run on the machine that produced the baseline.
- Alternatives considered: The median alone (flips between modes, so identical code can show a 30–50% change); the fastest run alone (hides slowdowns that come from more allocation and garbage collection); dropping runs that include garbage collection (`filter_gc = TRUE`, which hides a real cost).
- Consequences: The baseline is regenerated on any new benchmark machine, which the pinned reference library allows at any time (about 30 minutes). From Phase 3 the gate measures the rewrite with the same measurement code (the harness needs a mode that runs the working tree instead of the reference library, added then) and runs the comparison.

### DEC-028: The data layer's object

### DEC-029: The exact tier requires bitwise identity of long vectors

- Date: 2026-10-02
- Status: accepted with the Phase 2 gate (2026-10-02)
- Context: Long double vectors in fixtures are stored as signatures (DEC-018), compared through their sums, extremes, and a sample. At the exact tier a change in one element can be absorbed by the sum and missed by the sample: a 1-ulp change in one value of a 7,944-row design column passed the comparison.
- Decision: At the exact tier (atol and rtol 0), the checksum of every value's bits (`bits_md5`) must also match. Other tiers are unchanged.
- Alternatives considered: Storing long vectors in full (the size budget, DEC-018).
- Consequences: No tolerance changes. No exact-tier case of the characterization suite stores a long double vector; the data-layer comparison relies on the stricter check, which then detected every deliberate corruption tried.
- Amended (Phase 8, step 1, 2026-10-06, under the project lead's delegation, with DEC-080): when the bit checksums of a vector match, the vectors are identical, and the stored summaries are not compared. The fixtures' sums and means were computed with x86_64's extended precision, which arm64 macOS lacks, so identical vectors gave different sums there (`4956d6c`). A vector whose checksum differs is compared through its summaries as before, and at the exact tier it fails.
- Confirmed (2026-10-07): the project lead confirmed the amendment (final review).

### DEC-035: Armadillo configuration of the compiled code

- Date: 2026-10-02
- Status: accepted with the Phase 3 gate (2026-10-03)
- Context: The C++ core must not include Rcpp headers (brief §5.6), so it cannot include Armadillo through RcppArmadillo, which configures Armadillo to print through Rcpp's streams and, on Windows, turns on Armadillo's own OpenMP. The reference compiled its numerical code with `#define ARMA_DONT_USE_OPENMP` (`src/Fixed_effect.cpp:5`, `src/Firth.cpp:5`); with Armadillo's OpenMP on, large sums would be accumulated in another order. Until Phase 4, `Firth.cpp`, the remaining part of `Fixed_effect.cpp`, and the generated `RcppExports.cpp` still include RcppArmadillo. The linker keeps one copy of each Armadillo template that several files instantiate, so a core routine can run a copy compiled in an old file: the first build of the core printed Armadillo's `solve()` warnings through Rcpp from core code, which inside a parallel region would call the R API from a worker thread.
- Decision: The core includes Armadillo only through `src/core/armadillo.h`, which reproduces RcppArmadillo's numerically relevant settings (BLAS and LAPACK called directly, 32-bit index words) without Rcpp, turns Armadillo's own OpenMP off as the reference does, turns Armadillo's warnings off, and sends Armadillo's output to a stream that discards it. `src/Makevars` and `Makevars.win` set `ARMA_DONT_USE_OPENMP` and `ARMA_WARN_LEVEL=0` for every file of the package, so every copy of a shared template is compiled with the same settings. In Armadillo 15.6 the warning level gates only messages and the symmetry check that `inv_sympd()` runs before its message, so no computation changes; the live comparison of the new routines with the old ones (bitwise identical) and the fixture tests confirm it.
- Alternatives considered: including RcppArmadillo in the core (forbidden by brief §5.6); keeping Armadillo's warnings in the core and routing them to R as warnings (needs a stream that is safe inside parallel regions, and the core reports its own conditions instead: non-convergence, rank deficiency, failed inversions).
- Consequences: Armadillo no longer prints warnings such as "solve(): system is singular; attempting approx solution" to the console, for the old code either; these went to the console only, never to an R condition, so no fixture is affected. The new fits report rank deficiency with `pprof_warning_rank_deficient` (D-38). When the last file that includes RcppArmadillo is rewritten, every file uses `src/core/armadillo.h` and the flags in `Makevars` become redundant.

### DEC-036: Shapes of the profiling API

- Date: 2026-10-02
- Status: accepted with the Phase 3 gate (2026-10-03)
- Context: The plan names the profiling functions (`provider_effects()`, `test_providers()`, `standardize_providers()`, `profile_providers()`, `funnel_limits()`) and ARCHITECTURE §B.4 and §E.1 say how family differences reach them, but not their exact arguments and results. The reference's `confint(option = "gamma")` allows only two-sided intervals; its funnel plot pairs score-test limits with flags from the modified score test at the first alpha (K-110); ARCHITECTURE §I.1 has `plot_funnel()` take either `profile_providers()` or `funnel_limits()`; and the toy model of the extension proof (DEC-024) has no `provider_test()` method but must run `test_providers()`.
- Decision:
  - Arguments follow NAMING §4. `null = NULL` means the family's default (`"median"` for fixed effects, 0 for random effects later), so one signature serves every family. `providers` selects by ID compared as character and rejects IDs the model does not include; the compatibility wrappers drop unknown IDs first, as the reference does.
  - `test_providers()` computes the exact, bootstrap, modified score, and Wald tests itself from the contract (expected outcomes, estimates, standard errors), and takes the standard score test from `provider_test()`, the hook for tests that need a model's internals.
  - `provider_effects()` gives two-sided intervals only, as the reference's `confint(option = "gamma")` does. `standardize_providers()` takes `alternative` and uses one-sided effect limits internally, as the reference's measure intervals do.
  - Measures tables have one row per standardization, measure, and provider, with `observed`, `expected`, and `variance` (indirect only), and record `population_rate` when rates are requested.
  - `funnel_limits()` returns the limits at each distinct provider precision for one or more levels, and the funnel points (`providers`): the indirect ratios, their precisions, and flags from the family's funnel test at the first level. The limits are computed by an internal function of alpha, so the wrapper can pass the user's alpha unchanged (K-110). `profile_providers()` collects the results of the other four functions, so `plot_funnel()` can take either object.
  - The family specification gains `direct_expected`, `funnel`, and `wald_caution` (NAMING §5), so the profiling code needs no branch on the model class.
- Alternatives considered: computing every logistic test in `provider_test()` (the toy model, which declares the exact test without implementing `provider_test()`, could not be profiled); one-sided `provider_effects()` (an interval the reference does not offer for provider effects); a wide `profile_providers()` table with a column per measure (columns outside the shared vocabulary).
- Consequences: the new API reproduces every logistic FE method fixture bitwise on this machine (Phase 3, step 3); ARCHITECTURE §B.4 is updated as built at the Phase 3 gate.

### DEC-038: Flagged benchmark tasks are re-measured against the reference in the same session

- Date: 2026-10-03

### DEC-043: Tolerances of the independent references and the metamorphic tests

- Date: 2026-10-03
- Status: accepted with the Phase 4 gate (2026-10-04), with the logistf tolerance of 1e-9 as proposed
- Context: The named tolerances in `tests/testthat/helper-tolerances.R` are for comparisons with the reference fixtures, and each changes only with sign-off (brief §3.3). The independent references of brief §6 E compute differently: `lm()` solves by QR on the full indicator design, direct lme4 calls repeat the adapter's computation, and logistf iterates to the same penalized maximum with its own steps and stopping rule. The metamorphic tests reorder sums. Measured in Phase 4: `fit_linear_fe()` against `lm()` at most 3.7e-13 relative; the four mixed fits against direct `lmer()`/`glmer()` calls bitwise identical, except the linear RE provider-effect SD, whose closed form (K-69) agrees with lme4's conditional SD to 4e-16; `fit_logistic_firth()` at `tol = 1e-10` against logistf (criteria 1e-12) at most 2.2e-11 absolute and 1.6e-11 relative on two datasets without extreme providers, with penalized log-likelihoods equal to 12 digits; row shuffles and order-reversing labels move the Firth estimates by at most 2e-15 relative with the same iteration count, and the linear FE estimates by at most 1.5e-14.
- Decision: `lm()`: the closed-form tier. Direct lme4 calls: bitwise identity, and the closed-form tier for the linear RE SD. logistf: atol 1e-9 and rtol 1e-9 on the estimates (a 45-fold margin over the measured agreement), and the closed-form tier for the penalized log-likelihood, which is insensitive to the estimates' last digits at the maximum. This tolerance lives with its justification in `tests/testthat/test-independent-fits.R`, not in `helper-tolerances.R`. Metamorphic tests: bitwise identity for the order of the providers' blocks and for labels that keep the providers' order (every fit), the iterative tier (Firth) and the closed-form tier (linear FE) for row shuffles and order-reversing labels; none for the lme4 fits, whose estimates move at the optimizer's precision under reordering (4e-9 relative for linear and up to 4e-4 for logistic models).
- Alternatives considered: the iterative tier for logistf (its absolute floor of 1e-12 fails for effects near zero, because two iterations that stop at different points agree only to about 1e-11); a looser logistf tolerance such as 1e-6 (would hide a small real discrepancy); an optimizer tolerance for reordered lme4 fits (would test lme4 rather than pprof, whose data handling the exact relations already check).
- Consequences: a failure of the logistf comparison means a difference larger than the stopping rules explain.

### DEC-046: The family specification carries the remaining family differences

- Date: 2026-10-04
- Status: accepted with the Phase 5 plan (2026-10-04)
- Context: ARCHITECTURE §B.4 makes the differences between families data in `profile_spec()` rather than code paths. Phase 3 built the fields logistic FE needs. Running the reference (PHASE5_PLAN.md, facts F3 to F10) shows the other differences: linear measures are differences (O − E)/n_i and (E − total)/n rather than ratios (K-83, K-84); the RE indirect numerator is the sum of lme4's fitted values (K-82, K-84); the linear FE direct reference total is Σ(γ0 + Zβ) and depends on the null (K-83); the logistic RE and CRE direct limits come from the C++ direct expectations, which differ from R's sums in the last bits (F5), while logistic FE's come from R sums (K-91); only logistic FE treats providers with no events or only events one-sidedly (F10); linear FE tests and intervals use normal or t(n − m − p) depending on the provider variance, in opposite ways (K-68, K-92, D-32); the covariate tests differ by family in distribution, degrees of freedom, the two-sided form (D-31), and the interval expression (lme4's for RE and CRE, F3); the linear funnel uses n_i, σ, no floor, and the Wald test (K-111).
- Decision: `profile_spec()` gains the fields `test_default`, `comparison` (`"ratio"` or `"difference"`), `direct_reference` (`"observed"` or `"null_expected"`), `direct_limits` (`"mean_function"` or `"direct_expected"`), `one_sided_extremes`, `wald` (the distribution and degrees of freedom of the provider tests and of the intervals), and `coefficient_wald` (the covariate p-value rule and interval rule); `funnel$precision` takes the observed size as a third argument. `indirect_numerator` accepts `"predicted"`, read through a new contract generic `predicted_outcome(model)`, whose `pprof_mixed` method returns the lme4 fitted values stored at fit time and whose default raises `pprof_error_unsupported_inference`. Every new field is optional, with a default equal to the Phase 3 behavior, so logistic FE and the toy model of the extension proof need no change; logistic FE states them explicitly anyway. The values per family are the table in PHASE5_PLAN.md, step 2.
- Alternatives considered: methods per family for measures and intervals (the scattered code paths §B.4 replaces); computing the RE numerator as `expected_outcome(model, provider_estimates(model))`, equal to lme4's fitted values on the example data (F4) but not guaranteed by lme4; one tail function with `df = Inf` for the normal distribution, bitwise equal (F7) but less readable than naming the distribution.
- Consequences: NAMING §5 lists the fields; ARCHITECTURE §B.4 and §E.1 are updated as built. A new model states its differences in its specification, and the extension proof shows that the defaults suffice for a model like the toy.

### DEC-048: Observed and expected in the measures tables of every family

- Date: 2026-10-04
- Status: accepted with the Phase 5 plan (2026-10-04)
- Context: In `standardize_providers()`'s table, `observed` and `expected` are the two sums a measure compares. For logistic FE these are Σy and the expected events. For the RE families the indirect numerator is the sum of the fitted values (predicted over expected, K-82, K-84, M-14), and for linear FE the direct reference total is Σ(γ0 + Zβ) (K-83), so `observed` would not always hold observed outcomes. The reference's `OE` tables call these columns `Obs` too.
- Decision: keep one schema: `observed` and `expected` are the numerator and denominator sums of each measure, as in the reference's `OE` tables, and the result records `indirect_numerator` (`"observed"` or `"predicted"`) and `direct_reference` (`"observed"` or `"null_expected"`) among its settings. The help states per family what the columns hold.
- Alternatives considered: a `predicted` column for RE indirect rows, with `observed` always Σy (clearer for RE, but the linear FE direct reference total would need another column, and the schema would vary by family).
- Consequences: one column layout for every family and a one-to-one map to the reference's `OE` tables, which the wrappers use; readers must check the settings to know which sums they see.

### DEC-050: The `glm()` independent check of logistic FE

- Date: 2026-10-04
- Status: accepted with the Phase 5 plan (2026-10-04)
- Context: ARCHITECTURE §G.5 plans a check of logistic FE against `glm(y ~ 0 + factor(provider) + Z, binomial)` on data without extreme providers, carried over from Phase 4. Measured (PHASE5_PLAN.md, F13): with `fit_logistic_fe(tol = 1e-12, stop_rule = "all")` and `glm.control(epsilon = 1e-14)`, estimates agree to 3.2e-13 absolute and 1.3e-13 relative (97 providers) and to 9.1e-15 (60 simulated providers), log-likelihoods are identical, and variances agree to 2.7e-13 relative once `glm()`'s covariance is evaluated at its own estimates (one more iteration started there); `glm()`'s reported covariance belongs to its previous iterate and differs by up to 9.3e-8.
- Decision: estimates within atol 1e-10 and rtol 1e-10 (a 300-fold margin over the measured agreement, as DEC-043 sets logistf's); variances, from `glm()` restarted at its estimates, and the log-likelihood within the closed-form tier. The tolerance lives with its justification in `tests/testthat/test-independent-fits.R`; the test skips nothing, `glm()` being in stats.
- Alternatives considered: the closed-form tier for the estimates (a three-fold margin for effects near 0); comparing with `glm()`'s reported covariance (would test `glm()`'s convergence point, not pprof).
- Consequences: the last independent reference of brief §6 E for the fits is in place.

### DEC-069: The documentation describes the operating characteristics of the RE and CRE tests and intervals

- Date: 2026-10-05
- Status: accepted (the project lead left the documentation part of M-20 to Claude's recommendation, 2026-10-05)
- Context: M-20: the simulation study (DEC-053, `validation/simulation-report.md`) finds the fixed-effect provider tests and intervals close to nominal, and the random-effect ones far from it: the RE and CRE Wald tests flag 0.7% to 0.9% of the providers without an effect at level 0.95, detect outlying providers less often than the FE tests (46% to 60% against 77% to 86%), and their intervals cover 99% of the providers without an effect but 38% to 45% of the outliers. The question has two parts: whether these characteristics are intended, which is the methodology owners', and whether the documentation describes them, which the project lead asked Claude to recommend. The tests divide the shrunken estimate (lme4's conditional mode) by its conditional standard deviation (K-69, K-70). For the linear random-intercept model with its variance components taken as known, a provider whose effect is 0 has α̂_i = R_i ē_i with R_i = σ²_α / (σ²_α + σ²/n_i) (K-69) and conditional standard deviation sqrt(R_i σ²/n_i), so its statistic is normal with mean 0 and variance R_i < 1; the interval α̂_i ± z·sqrt(R_i σ²/n_i) is the posterior interval of α_i, which covers α_i with probability above the level when α_i is near 0, below it when |α_i| is large, and at the level on average over effects drawn from N(0, σ²_α). This is the standard behavior of empirical Bayes intervals.
- Decision: the documentation describes these characteristics, and no procedure changes. (1) The methods vignette derives them for the linear random-intercept model, as above; computes, for the providers of the example fit, the probability that the test flags a provider without an effect (2(1 − Φ(z_{1−α/2} / sqrt(R_i)))); says that the logistic RE and the CRE models behave in the same way, approximately for the logistic ones; cites the literature on empirical Bayes intervals and on identifying unusual providers with hierarchical models; and reports the repository's simulation study with its settings. (2) The help of `test_providers()`, `provider_effects()`, `standardize_providers()`, and `profile_providers()` says, for random-effect models, that the tests and intervals use the shrunken estimates and their conditional standard deviations, and points to the vignette. (3) The getting-started and models vignettes say that the flags of random-effect and fixed-effect models answer different questions and are not interchangeable. Whether these characteristics are intended, and any change to the procedures (Class B), stays with the methodology owners (M-20 remains open on that part).
- Alternatives considered: saying nothing (the proposed default: users could read RE flags and intervals as calibrated for each provider, as the FE ones are, and base a profiling decision on that reading); the simulation's numbers alone (they depend on its settings, while the derivation does not); changing the procedures (Class B, the owners').
- Consequences: the statements rest on a derivation that the vignette shows, a computation on the example fit, cited literature, and the simulation study; the wording list of the check-in includes them.

### DEC-083: The exact test's statistic is compared on its tail probability

- Date: 2026-10-07
- Status: accepted by the project lead (2026-10-07), as recommended in the final review (option (a) for D-53); a tolerance change with the project lead's sign-off (brief §3.4)
- Context: On Linux, the per-platform reference jobs (DEC-080) found the package's exact-test statistics outside the iterative tolerance of pprof 1.0.3's on the same runner, in one to three cases depending on the run (`test-binary-exact-null0`, `test-binary-exact-null-integer`, `test-medium-exact`; up to 1.3e-4 absolute), with every p-value, flag, and other column within it (D-53). The statistic is `qnorm(p)` of a tail probability `p = 1 - ppoibin(o, probs) + dpoibin(o, probs) / 2`, computed with an absolute error of a few units in the last place of 1; `qnorm()` multiplies an error in `p` by `1 / dnorm(z)`, 2e14 at z = 8, so for an extreme provider the statistic is determined by the arithmetic only to that precision. OpenBLAS rounds 52 of the 7,944 rows of the example data's linear predictor differently when it multiplies by provider and over the whole design (D-53), which is enough. Measured on the fixtures' platform (`dev/design/phase8-facts/11_exact_statistic_rule.R` and its output `.txt`): last-bit noise in the linear predictor moved up to 16 of the 1,000 statistics of the 80,000-row case beyond the iterative tolerance, by up to 4.2e-3 at z = 7.8, and none beyond it on the tail probability; the same rule rejects a shift of the null by 1e-9 on the logit scale for 68% to 93% of the providers of each case.
- Decision: The statistic of an exact Poisson-binomial test (test()'s default for logistic FE and Firth fits, `test = "exact.poisbinom"`) matches its reference when it is within the case's tolerance, or when it has the reference's sign and its tail probability `pnorm(-|z|)` is within the case's tolerance of the reference's: the scale on which it is computed, and on which its p-value is already compared. The rule (`pprof_exact_statistic` in `tests/testthat/helper-tolerances.R`, `reference_compare_exact_statistic()` in `helper-equivalence.R`) applies to the `stat` column of those cases only, in the tests, `validation/run-reference.R` (whose report lists the cases that match only on the tail probability), and `validation/run-differential.R`. No other tolerance changes; no fixture changes.
- Alternatives considered: a wider absolute or relative tolerance on the statistic (it would loosen every other statistic's comparison or still fail at the extremes, where `1 / dnorm(z)` grows without bound); reproducing the reference's grouping of the linear predictor by provider (needs the design matrix, which models keep only with `keep_data = TRUE`, and changes the package's arithmetic for a comparison artefact); keeping the cases failing on Linux.
- Consequences: The 14 exact-test cases (13 core, `test-medium-exact` in the full set) compare their statistics on the tail probability; on the fixtures' platform none needs it (every statistic is within the iterative tolerance). For an extreme provider the comparison is no tighter than that of its p-value, which was already the case.

### DEC-099: The robust variance comes from survival's dfbeta residuals on the fitter's result

- Date: 2026-10-08
- Status: accepted by the project lead (2026-10-08, with the C2 plan, its decision 1); amends DEC-091; answers DEC-098's search
- Context: DEC-091 computed the robust variance by calling `coxph()` with an explicit cluster, which took 129.7 s at 1,000,000 rows in C1's baseline (DEC-098) and 20.7 s on rows sorted by provider in the plan's evidence. `coxph()`'s robust step applies survival's `residuals.coxph(type = "dfbeta", collapse = cluster, weighted = TRUE)` to an object it builds from its fitter's result, then `crossprod()`; the rest of `coxph()` builds a model frame, computes the concordance, and adds a robust score test at β = 0, none of which the package uses.
- Decision: The adapter does exactly that with its own fitter result: the fitter's list with `x`, `y`, `weights`, `strata`, and `terms`, of class `coxph`, passed to `residuals()` with the cluster codes (one cluster per fitted row when no cluster is given), then `crossprod()`. - Consequences: The robust variance equals `coxph()`'s bitwise, with one cluster per row and with a cluster column, for both fitters (`dev/design/coxph-facts/17_robust_from_fitter.txt`; the engine-identity tests). It relies on what `residuals.coxph()` reads from `coxph()`'s internal object; the engine-identity tests pin that, and if a later survival breaks it, the fit returns to DEC-091's `coxph()` call.

### DEC-101: The covariate p-value of Cox fits is computed as an upper tail

- Date: 2026-10-08
- Status: accepted by the project lead (2026-10-08, with the C2 plan, its decision 3)

The package's default covariate rule, logistic fixed effects' 2(1 − Φ(|z|)) (K-100), gives 0 for |z| above 8.3; the `lt-stratified` fixture has a coefficient with z = 9.15 and p = 5.5e-20.

- Alternatives considered: the default rule (p-values of 0 where pprof_py reports values below 1e-16, a Class B difference).
- Consequences: The Cox coefficient table reproduces pprof_py's p-values; the existing families' tests are unchanged.

### DEC-105: The 10% rule compares a Cox fit with its engine call plus the preparation of the engine's inputs

- Date: 2026-10-09
- Status: accepted by the project lead (2026-10-09, C2 gate), as recommended in the gate report; it changes how decision 7 of the C2 plan (DEC-100) is read; C3 times each fit with its measures against the engine call, the preparation of its inputs, and the measures (DEC-111). The final runs (DEC-136; `dev/bench/results/cox-final-20261016.md`): every fit meets the rule in its latest run, the two fits at its line on the C3 runner and the Fine–Gray fits on the C6 runner.
- Context: The brief's §3.7: "A `pprof` fit MUST NOT be more than 10% slower than the direct engine call it wraps plus the measures." The C2 plan's decision 7 (DEC-100) took as the comparator survival's fitter on the inputs the adapter builds, prepared outside the timing, as C1's baseline timed the engines. In the paired runs (`dev/bench/results/cox-c2-paired-20261009-windows.md`: seven of C1's eight scenarios, two rounds; the corner could not be measured on this machine, which paged), every fit's estimates equal its engine call's bitwise, and 17 of the 21 fits are too slow by DEC-038's rule: their medians are 1.0 to 2.3 times the engine call's at 100,000 rows and 1.2 to 1.5 times at 1,000,000; the other four pass by the 0.05 s floor (10,000 rows) or by one round's noise. The excess is the preparation of the inputs from the data frame, `data_prepare()` and the adapter's inputs, 0.1 to 0.4 s at 100,000 rows and about 2 s at 1,000,000: against the engine call plus that preparation, no fit is too slow. In one process (`dev/design/coxph-facts/21_fit_time_parts.txt`), the model frame that any formula interface builds takes 13% of the fitter's time at 20 covariates and 28% at 5; `data_prepare()` as a whole 27% to 33% at 20 covariates and 71% at 5; the adapter's inputs 6% to 19%; the finite check of the design 2% to 4%; the model object 1% to 4%. Against `coxph()` on the data frame, the call a user would make, the fits take 0.2 to 0.5 of its time.
- Decision: The rule compares a Cox fit with its engine call plus the preparation of the engine's inputs from the user's data (the formula, the model frame, the design, and the inputs in the engine's form), which a direct call of the fitter on a data frame also needs: a fit is too slow when, in every round, its median and fastest run are more than 10% above that sum and its median at least 0.05 s above (DEC-038). The paired report gives both readings; under this one, the C2 fits meet the MUST.
- Alternatives considered: (1) keep the plan's comparator, and record that the Cox fits do not meet the MUST; (2) a data path for survival data that bypasses R's model frame for numeric covariates: a second path beside the one every family shares (COXPH_DESIGN §C.2 keeps one), and with the model frame's 13% gone, the sort by provider and the adapter's inputs still take more than 10% of the fitter; (3) trimming the adapter's own steps, with the same results: its inputs (10% of the fitter at 1,000,000 rows) built with fewer copies and the strata codes by an integer match rather than `factor()`, a few percent of the fitter, worth a later performance change but not enough for (1); (4) `coxph()` as the comparator, which the fits beat by a factor of 2 to 5, against the brief's distinction between the engine (6.3 s) and its formula interface (18 s).
- Consequences: `dev/bench/cox/summarize_paired.R` gives this verdict as the MUST's, with the verdict against the engine call alone beside it, and C3 times the measures the same way (the rule's "plus the measures"). The corner scenario, which this machine could not measure, is measured at the C3 gate on a machine with enough free memory (the project lead, 2026-10-09).

### DEC-107: The funnel of Cox models is pprof_py's, and its limits are in the Cox fixtures

- Date: 2026-10-09
- Status: accepted by the project lead (2026-10-09, with the C3 plan, its decisions 1 and 2); re-decides M-39
- Context: M-39 chose normal limits, 1 ∓ Φ⁻¹(1 − α/2)/√E_j with a floor of 0, for "Cox models, which pprof_py lacks". pprof_py v0.7.0 has them: `CoxPH.funnel_limits()` (`inference/survival/provider_tests.py:142-172`, `inference/funnel.py:poisson_funnel_limits`), which neither the brief's §2.4 nor COXPH_DESIGN §A recorded. At each expected count E it takes the largest count its test flags low and the smallest it flags high, under the test's own Poisson null, and sets the limits half-way between counts, so that a provider lies outside its limits exactly when it is flagged. M-39's limits disagree with the mid-p flags: on the `provider-scale` fixture, 11 to 13 of 1,000 providers lie outside them unflagged and 2 flagged ones inside (`dev/design/coxph-facts/23_funnel_limits.txt`).
- Decision: The funnel of Cox models is pprof_py's (K-149): the points are the indirect ratios O_j/E_j with precision E_j; the limits at each distinct E > 0 and level are (o_lo + ½)/E and (o_hi − ½)/E under the mid-p test, or −∞ and ∞ where no count is flagged; the flags are the mid-p test's at the first level; `target` must be 1. The table keeps the package's shape, one row per level and distinct provider precision, where pprof_py's curves use a 200-point grid of E (a presentation difference); at each provider's E the limits equal pprof_py's for that provider. The Cox fixtures record pprof_py's limits: the generator (`dev/reference/cox/generate.py`, `0bf2a54` and `7c0fe61`) adds `funnel` to every Cox case and cause-specific record (each provider's limits and flag at level 0.95, and, in the full set, which is not shipped, the curves at 0.95 and 0.998), and both sets were regenerated (`4e7f246`): the diff reports (`dev/reference/diff-reports/20261009-cox-funnel-core.md`, `-full.md`) show only the added element, and a second generation reproduced the first.
- Alternatives considered: M-39 as decided (a Class B difference from pprof_py, points and flags disagreeing as D-43 describes for linear fixed effects); the curves in the shipped set too (they took the tarball to 4,986,258 bytes, 14 KB under the 5 MB at which `R CMD check --as-cran` notes it, DEC-076).
- Consequences: the funnel agrees with the flags by construction, as pprof_py's does; `test-cox-reference.R` and the calibration report compare its limits with pprof_py's exactly; the shipped set grows by 1.3 KB.

### DEC-108: `count_distribution` selects the Poisson tests, limits, and funnel; no `measure_limits` field

- Date: 2026-10-09
- Status: accepted by the project lead (2026-10-09, with the C3 plan, its decision 3); amends DEC-092
- Context: DEC-092 added three optional fields to the family specification: `count_distribution`, `measure_limits` (a function giving the limits of the measures), and `direct_by_provider`. The model files are layer 2 and the inference layer 3 (ARCHITECTURE §B.1), and `test-architecture.R` checks every call of a file, closures included, so a `measure_limits` function in the Cox model's specification could not call the Poisson limits, which invert the tests that COXPH_DESIGN §D.3 item 4 puts in the inference layer.
- Decision: `count_distribution = "poisson"` selects, in the profiling layer, the Poisson tests (K-140 to K-142), the limits of the indirect ratios (Garwood's or Byar's, and the mid-p limits), and the funnel's limits (K-149), all from `R/inference-poisson.R`; tests and intervals are two-sided, and direct standardization has no intervals. There is no `measure_limits` field. `direct_by_provider(model, rows)` gives the direct expectation of each provider in `rows` for a family without provider effects (K-138). The defaults, `count_distribution = "poisson_binomial"` and `direct_by_provider = NULL`, are the existing families' behavior.
- Alternatives considered: `measure_limits` holding the inference layer's functions by reference (a model depending on a higher layer, which the architecture test would not see); the Poisson limits in the model layer (separates the limits from the tests they invert).
- Consequences: one field says the counts are Poisson, and the tests, limits, and funnel follow from it; NAMING §10 and COXPH_DESIGN §D.2 and §D.3 record the hooks as built.

### DEC-110: The mid-p limits are found once per distinct observed count, to rounding

- Date: 2026-10-09
- Status: accepted by the project lead (2026-10-09, with the C3 plan, its decision 5); the root search became the plan's fallback after the C3 benchmarks (below)
- Context: The brief's §3.7 requires mid-p intervals substantially faster than pprof_py's (50 s at 3,000 providers in C0). pprof_py finds each provider's limits with Brent's method on a bracket of its own. On the Poisson-mean scale the limits are the roots of 2Φ̄(|z(O, t)|) = α, which depend on O alone; the bracket and the tolerance only set how precisely they are found (`dev/design/coxph-facts/22_measures_tests.txt`).
- Decision: The package finds the two roots of each distinct observed count once, to rounding, keeps pprof_py's decisions of 0 for the lower limit and ∞ for the upper where its equation is not negative at its bracket ends for that provider, and divides by each provider's E_j (K-141). The plan's §3.3 found the roots with `uniroot()` one count at a time; in the C3 benchmarks the mid-p test with its limits was then only 8 times faster than pprof_py's at 100 providers, where nearly every provider has a count of its own (DEC-111 asks for ten). So the package bisects over all the distinct counts at once, the fallback the plan's §8 named: the same roots to rounding, at most 17.5 ulp apart at level 0.95 and 185 at 0.998, with the same decisions of 0 and ∞ at seven levels, 4 to 7 times faster (`dev/design/coxph-facts/24_midp_bisection.txt`).
- Alternatives considered: pprof_py's algorithm per provider with `uniroot()` (within 0.47 of pprof_py's xtol, but 5.0 s at 3,000 providers); `uniroot()` once per distinct count (the plan's first choice, too slow where the counts are mostly distinct).
- Consequences: the limits are within 0.25 of pprof_py's xtol of pprof_py's (fact 22, found with `uniroot()`; the bisection's roots agree with those to rounding), inside `cox_root`; with `uniroot()` on the same synthetic data they took 0.22, 0.43, and 0.42 s at 1,000, 3,000, and 7,500 providers, where pprof_py took 21.6, 62.6, and 184.6 s. The time grows with the number of distinct counts: by bisection, 0.03 s for 100 of them and 0.17 s for 1,000.

### DEC-113: The glmnet adapter's other calls

- Date: 2026-10-14
- Status: accepted by the project lead (2026-10-14, with the C4 plan, its decision 1)

### DEC-114: The fold deviances come from one coxnet.deviance() call per fold and set of rows

- Date: 2026-10-14
- Status: accepted by the project lead (2026-10-14, with the C4 plan, its decision 2)
- Context: pprof_py's fold deviance (K-144) takes the partial likelihood at each fold's coefficients on all rows and on the training rows, with the Breslow saturated term for both tie methods; COXPH_DESIGN §E.2 took Breslow deviances from `coxnet.deviance()` and Efron ones from the partial likelihood. One survival evaluation per fold, set of rows, and grid point reproduces the generator's R side bitwise but takes 57% of a 10-fold cross-validation on `covariates-50`. `coxnet.deviance()` takes every grid point's linear predictor at once; its saturated term is pprof_py's with Breslow ties and differs by a constant of the rows with Efron ties (830.15 on `penalized-combined`, the same for 100 linear predictors within 1e-11; facts 27 and 28).
- Decision: Each set of rows gets one `coxnet.deviance()` call over all the fold's grid points, moved to pprof_py's saturated term by subtracting its value at the offsets less 2 (lsat - loglik), with lsat pprof_py's Breslow form summed in the package and loglik survival's partial log-likelihood of the offsets (`survival_partial_loglik()`).
- Alternatives considered: one survival evaluation per fold, set of rows, and grid point (the generator's way; about 1.6 times slower on `covariates-50`); the design's split by tie method (two code paths, the Efron one as slow as the first alternative).
- Consequences: the fold deviances within 3.2e-13 of the generator's R side, the same lambda_min and lambda_1se, and an estimated 211 s for a 10-fold cross-validation on `covariates-50`, where pprof_py took 1,717 s in C1; a later glmnet that changes its saturated term is absorbed, since the shift is measured at every call.

### DEC-115: glmnet's early stops and failed solutions end the path

- Date: 2026-10-14
- Status: accepted by the project lead (2026-10-14, with the C4 plan, its decision 3); registers D-78; D-78 signed off by the project lead as methodology owner (2026-10-19, DEC-142)

### DEC-122: finegray() is called once per chunk of 50 providers

- Date: 2026-10-15
- Status: accepted by the project lead (2026-10-15, with the C5 plan, its decision 2); amends COXPH_DESIGN §E.3; extends DEC-098 to the Fine–Gray fits
- Context: survival 3.8-12's `finegray()` goes over all its rows once per stratum, in `survfit()`, `[.survfit`, and `split()`, so one call stratified by provider takes time that grows with rows times providers: 24 s on 100,000 rows of 1,000 providers, and 109 to 178 s with 7,500, where pprof_py's whole fit takes 5.3 s and 6.4 s (`dev/design/coxph-facts/33`, `34`). One call per provider decides delayed entry per provider, where `finegray()` decides it over all rows, and so can give other pieces and weights (fact 31's counterexample; one row fewer on `providers-7500`). Apart from that decision, `finegray()` computes each stratum from its own rows (its source, `R/finegray.R`).
- Decision: `finegray()` is called on the providers in chunks of 50 (`fine_gray_chunk_providers`), in provider order. When the data have delayed entry by `finegray()`'s rule (some subject's first row, by subject and exit time, enters later than the smallest exit), every chunk also holds the provider of the smallest exit and that of the first such subject, so that it decides as all rows do; each chunk keeps its own providers' rows. A chunk without an event of the cause is skipped, as `finegray()` leaves such providers out.
- Alternatives considered: one stratified call (survival's definition by construction, but minutes at thousands of providers); one call per provider (faster, but a Class B difference where it decides delayed entry otherwise).
- Consequences: the chunks give one stratified call's expansion bitwise in every case of fact 35 (3 to 14 times faster) and in the engine-identity tests, which lower the chunk size so that the data take several chunks and include fact 31's counterexample (`test-model-survival.R`). The rule restates `finegray()`'s; a later survival that changed it, or computed a stratum from other rows, would fail those tests, and the fix would be one call. The brief's §3.7 SHOULD (no slower than pprof_py) is not met everywhere, as DEC-098 allows for large fits (DEC-127).

### DEC-123: finegray()'s settings

- Date: 2026-10-15
- Status: accepted by the project lead (2026-10-15, with the C5 plan, its decision 3); registers K-145, D-58, D-74
- Context: survival 3.8-12's `finegray(weights = w)` multiplies its output weights by `user.weights[split$row]`, where `split$row` counts the rows of the stratum, so every stratum after the first gets the case weights of the data's first rows (fact 31, part B). `finegray()` merges near-tied times by default (`timefix = TRUE`), refuses a status with a single event type, and needs a multi-state `Surv()` response, whose status is a factor; `Surv()` reads a numeric status coded 0/1/2 as one event type. pprof_py multiplies the transform's weights by each row's case weight, keeps rows of weight 0 in the transform and passes them to its Cox fit with weight 0, and fits a 0/1 status.
- Decision: `timefix = FALSE` (M-23). No `weights` argument: the expanded rows' weights are `finegray()`'s times their observations' case weights (K-145), whose censoring and entry distributions stay unweighted. Rows of weight 0 stay in the transform, and their pieces leave the fit (M-25, D-58). The status is a factor whose first level is censoring, `Surv()`'s multi-state coding; a numeric status raises, with the hint `factor()` (D-74). `cause` is one of the event types, by label or by a number equal to it. A single event type is accepted, with an unused second level added for `finegray()`, which then returns the rows unchanged with weight 1, as pprof_py fits a 0/1 status.
- Alternatives considered: `finegray(weights =)` (wrong after the first provider); refusing zero weights, as `coxph()` does.
- Consequences: the expansion's rows and status equal pprof_py's exactly, and its times and weights within `closed_form`, on every competing-risk record, the weighted case's included; a single event type gives the stratified Cox model clustered by subject within 1e-12 (`test-model-fine-gray.R`); the case weights' product is tested against `finegray(weights =)` in its first provider and against the product elsewhere (`test-model-survival.R`).

### DEC-124: The inputs that finegray() does not check follow pprof_py

- Date: 2026-10-15
- Status: accepted by the project lead (2026-10-15, with the C5 plan, its decision 4); registers D-80
- Context: `finegray()` needs an `id` for any (start, stop] data, ignores it for right-censored data (a repeated `id` passes), and does not check that a subject stays in one provider; with delayed entry in small providers its weights can be NaN or infinite (33 pieces in 22 providers of `rows-1e4`, 207 on `providers-7500`). pprof_py needs `id` only when an entry time is not 0, rejects a repeated `id` with right-censored data and a subject that changes strata, and raises `FloatingPointError` where the probability of being under observation is 0 before a competing event, also where no later piece follows and survival's weights are all finite (facts 31 and 33).
- Decision: (start, stop] data need `id` when an entry time is not 0; otherwise each observation is its own subject, and `finegray()` gets the observations as subjects. A repeated `id` with right-censored data, and a subject in two providers, raise `pprof_error_invalid_input`, as do `finegray()`'s own errors, with survival's message in `engine_message`. Weights that are not finite raise `pprof_error_data`, whose `providers` names the providers (D-80). No `offset()` terms, since pprof_py's `FineGrayPH` takes none; no `cluster` or `robust` argument, the variance being robust and clustered by subject.
- Alternatives considered: survival's own rules (an `id` for any (start, stop] data, a repeated `id` accepted with right-censored data); raising wherever pprof_py raises, which needs pprof_py's test of the probabilities, a computation of the package's own.
- Consequences: where pprof_py raises without a later piece and every weight is finite, the package fits (D-80, Class A): on the benchmark's `covariates-5` data pprof_py raises and the package fits; on `providers-7500` as generated, both raise, and on `rows-1e4` the package does.

### DEC-147: The contract and the profiling hooks for binomial outcomes and clusters

- Date: 2026-10-20
- Status: accepted under DEC-143 (best judgement), with the L0 design
- Context: The profiling and inference layers read models only through the contract (ARCHITECTURE §B.1). Binomial tests need each trial's probability and the number of trials, which `expected_outcome()` does not give: n p cannot be divided back into p without rounding, while pprofR computes p first. The clustered tests need each observation's cluster.
- Decision: three contract generics, `observation_trials()` and `observation_clusters()` with shared methods that read the model (`NULL` when absent), and `trial_probability()`, implemented by the logistic fixed-effect model. The profiling and inference functions take a binomial branch when `observation_trials()` is not `NULL`, and a clustered branch when `se_type` is not `"model"`, each in new functions beside the existing ones, which keep their code. The family specification of a binomial model carries its weights in `direct_expected`, sets `direct_limits = "direct_expected"`, and adds an optional `direct_moments` for the standard errors of direct measures. Two capabilities, `variance_robust` and `variance_stabilized`, are declared by logistic fixed-effect models with clusters.
- Alternatives considered: `expected_outcome()` returning probabilities for binomial models (contradicts its meaning, the expected outcome of an observation); the profiling layer computing probabilities from the family's mean function (reads the effects through a helper, not the contract); one capability per clustered test (seven names for two variance estimators).
- Consequences: a model of another package keeps working unchanged; the toy model's extension test stays as it is.
