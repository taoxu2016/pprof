# Developer guide for contributors to pprof

For people who change pprof itself. To add a model, read the vignette "Adding a model to pprof" first (`vignettes/adding-a-model.Rmd`, `vignette("adding-a-model", package = "pprof")`); this page is the map of the repository and of the rules behind it, and links to the documents that hold the details rather than repeating them.

## The rule that comes first

pprof 2.0 is a rewrite of pprof 1.0.3 that preserves its statistical behavior exactly. The reference is pprof 1.0.3, commit `5260838`, and its results are the specification: estimates and iteration paths, variances, tests, p-values, intervals, standardized measures, flags, screening, provider order, and defaults. Every difference from it, intended or found, is recorded in `dev/DISCREPANCIES.md` with a class:

- A: pprof 1.0.3 crashed, returned `NULL`, misaligned results, or was nondeterministic. May be fixed, with a regression test.
- B: any change to a number, flag, inclusion decision, or default. Not made without written sign-off by a methodology owner; until then the code reproduces pprof 1.0.3.
- C: documentation or messages contradict behavior. The documentation is fixed.

A discrepancy is never resolved by loosening a tolerance, editing a fixture, or dropping a test case. `CLAUDE.md` and `.claude/rules/tests.md` state these rules, which the v2 rewrite's brief set (`dev/README.md`); `dev/DECISIONS.md` records the decisions made under them.

The Cox models, added in the CoxPH phase (`dev/coxph_brief.md`, whose §3 is their equivalence contract), have a second reference: pprof_py v0.7.0 (commit `9320766`), the group's Python package, whose behavior they reproduce, with estimation delegated to survival and glmnet. Their differences from pprof_py are in the CoxPH section of `dev/DISCREPANCIES.md`, with the same classes, and their conventions in `dev/CONVENTIONS.md` (K-131 to K-149).

## Changing code

- Find the layer the change belongs to; a layer calls only its own and lower layers, and the profiling and presentation layers read models only through the model contract and results only through their fields.
- Name things from the vocabulary of `dev/NAMING.md`; sibling functions share argument names, order, and defaults.
- Check arguments at the boundary and raise classed conditions (`pprof_error_*`, `pprof_warning_*`); print nothing unless `verbose = TRUE`.
- Name every numerical constant, with its contract and its reference location.
- Constructors are `new_pprof_<class>()` and validators `validate_pprof_<class>()`; constructors return their object visibly.
- If a change could alter a number, compare with the fixtures and the differential tests before anything else, and record any difference in the register before deciding what to do with it.
- Record user-visible changes in `NEWS.md`.

## Delegated engines

The random-effect models delegate their estimation to lme4, the Cox and Fine–Gray models to survival, and the elastic-net Cox model to glmnet. The engine owns the likelihood and its optimization; the package owns the data, what it derives from the engine's results, and the profiling (DEC-086). The adapters are the lme4 section of `R/model-mixed.R`, `R/model-survival.R`, and `R/model-glmnet.R`, each with a header naming the decisions behind it.

Estimation is delegated when a maintained package fits the model and its results can be matched with the reference's; the package writes its own engine (in C++, ARCHITECTURE §F) only when no package fits the model at the scale needed, as for the logistic fixed effects, whose thousands of provider effects SerBIN fits with the information matrix's block structure, and for the Cox model with explicit provider effects (the CoxPH brief's §2.2: `coxph()` with provider indicators took 144 s at 1,000 providers). A later model that delegates follows the rules the three adapters follow:

1. **One adapter per engine.** The adapter holds every call that fits a model or prepares the engine's inputs, in functions named after the engine, `lme4_*()`, `survival_*()`, `glmnet_*()`; the engine's name is allowed in adapter names only (NAMING §2), and a new engine's name joins that list. A new call to an engine the package already uses goes in that engine's adapter. Model files call the adapter, and call the engine's user-level functions only on objects the adapter built (survival's `survfit()` for the curves); `check_data()` calls survival's `aeqSurv()` to report what `coxph()` would merge.
2. **Call the engine as its own user-level function calls it.** lme4 is called through `lmer()` and `glmer()` as pprof 1.0.3 called them (K-50). survival's fitters, `coxph.fit()` and `agreg.fit()`, are called with the arguments `coxph()` passes them: the offset minus its mean, `nocenter`, integer strata codes in provider order, clusters coded as `coxph()` codes them (DEC-100). The results are then the user-level function's bitwise, and a test can say so. Calling below the user-level function needs evidence that it pays (DEC-091: `coxph()` took three times its fitter's time). The survival and glmnet adapters give the engine the prepared data, `data_prepare()`'s design matrix, response, and provider codes (under generated names where the engine takes a formula), so that the engine fits exactly the rows and columns the model describes; the lme4 adapter gives lme4 the user's columns, because pprof 1.0.3 did.
3. **Take what the engine computes from the engine.** Where a quantity needs the user-level object, the adapter builds that object with the fit's settings (`survival_engine_fit()`), or applies the user-level function's own step to the fitter's result (the robust variance, DEC-099). Where the reference needs a quantity the engine does not return, it is composed from the engine's documented routines (glmnet's `coxgrad()` and `coxnet.deviance()`, DEC-113, DEC-114). The package computes nothing of the fitted model that the engine provides: no partial likelihood, Newton step, variance, residual, or baseline hazard of the fit (the CoxPH brief's §1; `baseline_hazard()` comes from survival's `survfit()`). What profiling computes from the engine's results is the package's own, by the brief's assignment (§2.1, §5.3, §5.4): the measures' expected events at the national Breslow baseline (`cox_expected_events()`, K-136, K-137), the Poisson tests and their limits, pprof_py's λ grid, and the saturated term of the fold deviances (K-143, K-144), as the logistic models' measures are. A later model's brief says on which side each of its quantities falls.
4. **Make every setting explicit.** Every option that can change a number is passed, never left to the engine's default: `timefix = FALSE`, the tie method, `eps`, and `iter.max` for survival; the grid, `cox.ties`, `standardize`, the penalty factors, and `control = list(thresh, maxit, fdev = 0, devmax = 1)` for glmnet (the CoxPH brief's §3.3 and §5.4). The engine's defaults can change between its versions; the package's must not. The lme4 fits are the exception that the reference made: they call lme4 as pprof 1.0.3 did, passing `...` and leaving lme4's defaults (K-50). A new adapter does not copy that.
5. **Classify what the engine says.** An engine error becomes `pprof_error_convergence`, with the engine's message in `engine_message` (`lme4_fit()`, `survival_abort()`, `glmnet_abort()`). A warning the package reports in its own words, such as an iteration limit, is muffled and replaced by one classed warning (`pprof_warning_not_converged`); other warnings pass through; lme4's messages are kept and shown only with `verbose = TRUE`. Whether a fit converged is read from the engine's result, not from its warnings: survival warns only when `iter.max > 1`.
6. **Check what the engine does not.** Inputs the engine accepts but the reference refuses or treats otherwise are checked before the call, with classed errors (DEC-124). A defect of the engine that the package works around is recorded with its evidence and covered by a test that fails if the engine changes (`finegray()`'s case weights, DEC-123).
7. **Keep only what the methods need.** The model keeps the estimates; the engine's object only with `keep_data = TRUE` (`engine_fit`). Methods that need it otherwise take the data the model was fit to as their `data` argument, rebuild the prepared data from it (`model_prepared_data()`, which checks it against the fit), refit the engine with the fit's settings, and check that the refit reproduces the coefficients (`cox_stratified_engine_fit()`; DEC-005).
8. **Import or suggest.** An engine that every installation needs is imported (lme4, survival). One that only some models need is suggested: each function that uses it calls `<engine>_require()` first, which raises `pprof_error_invalid_input` with a `package` field, naming the package and its minimum version (`glmnet_require()`, DEC-088); `<engine>_available()` gives the tests and examples their skips.
9. **Pin the versions relied upon.** DESCRIPTION states the version from which the engine computes what the adapter relies on (survival 3.8-11, DEC-106; glmnet 5.0), and the adapter's comments name the version whose source they follow.
10. **Test the adapter against the engine, bitwise.** The engine-identity tests compare each fit with the engine's user-level function on the same data, with no tolerance: `expect_identical()`, or the `cox_engine` tier (atol and rtol 0): `test-independent-fits.R` for lme4, and `test-model-survival.R`, `test-model-glmnet.R`, and `test-model-fine-gray.R` for survival and glmnet. A new engine's identity tests use `expect_identical()`; the tiers of `helper-tolerances.R` change only with sign-off. A new engine version that moves a number fails these tests before any comparison with the reference, and the fixtures' manifests record the engine versions they were made with.
11. **Benchmark against the engine.** The CoxPH brief's §3.7 allows a fit at most 10% more time than the engine calls it makes plus the preparation of their inputs, on the same data in the same session, by DEC-038's test with its 0.05 s floor (DEC-105), so that what is measured is the package's own cost. A later brief sets its own rule.

The rest of a delegated model is an ordinary model module: the model contract, the family specification, and the capabilities (the vignette "Adding a model to pprof"); the hooks the Cox models added to the contract are in ARCHITECTURE §E.6. Inside pprof, a model uses the shared helpers: the argument checks `check_*()` (`R/validate.R`), the conditions `abort_*()` and `warn_*()` (`R/conditions.R`) and the messages of `inform_message()` (`R/messages.R`), and the model helpers `model_*()` (`R/model-class.R`). `spec$family` names the model, and `profile_spec()$family` the family specification it is profiled with, which a subclass may inherit: `fit_logistic_firth()`'s models have `spec$family` `"logistic_firth"` and are profiled as `"logistic_fe"`, whose method fixes that name.

**Files a new model touches.** Its `R/model-<name>.R`, its tests, and its help; DESCRIPTION when it brings an engine (Imports or Suggests); `_pkgdown.yml`, whose reference index lists every topic, so that pkgdown refuses a topic missing from it; the presentation files for its own `print()`, `glance()`, and `augment()` (ARCHITECTURE §E.4); `NEWS.md`; `dev/NAMING.md` for its names; the registers; ARCHITECTURE §E.3's capability table; and this guide's tables. `NAMESPACE` and `man/` are generated.

**Models fitted to expanded rows.** The Fine–Gray model fits survival's expansion of the data (`finegray()`), and its observations are still the input rows: `data_prepare()` prepares the input rows, the adapter expands them, the per-observation fields (`row_index`, `response`, `linear_predictor`) describe the input rows, the expansion's size is a field of its own (`n_expanded`), and the methods per expanded row (`residuals()`, `augment()`) are refused (D-81). `validate_pprof_model()` requires `row_index` to give each observation's row of the input data, and the methods that take `data` rebuild the prepared data from the input data (`model_prepared_data()`). A model whose observations are the expanded rows, such as person-periods, departs from this pattern; its brief decides what an observation is, and how those methods rebuild the expansion.

### The later models

The CoxPH brief's §2.2 lists the models that wait for briefs of their own; each needs a methodology sign-off and a reference before it is built. Where no external reference exists, the brief names the validation that stands in for one: engine identity, an independent implementation, and the simulation study (`validation/run-simulation.R`), among the test layers of `.claude/rules/tests.md`. Where each would start:

| Model | Estimation | What it adds | Where to start |
|---|---|---|---|

| Penalized provider models (group lasso Cox, provider-penalized Cox, discrete-time) | the package's own engine | a path over λ and its selection, as the elastic-net model has them | ARCHITECTURE §E.5 (the path rules), `R/model-cox-penalized.R` and `R/model-cox-selection.R` (`select_lambda()` is a generic); grplasso's code could be copied only if its authors relicensed it (GPL-3, pprof MIT) |
| Unpenalized discrete-time provider models | the logistic fixed-effect engine on person-period rows | an expansion of survival data into one row per person and period: in the data layer if the package computes it, in an adapter if an engine's function, such as survival's `survSplit()`, does (rule 1) | `fit_logistic_fe()`'s internals, as `fit_logistic_firth()` uses them (`logistic_fe_estimate()`, `logistic_fe_model()`); the data layer's survival data (`R/data-survival.R`); "Models fitted to expanded rows" above. ## Continuous integration

`.github/workflows/`, run on pushes and pull requests to `main`, `rewrite/**`, `coxph/**`, and `logistic/**` (DEC-071; the CoxPH brief's §12; the logistic extensions brief's §12):

- `rewrite-check.yaml`: `R CMD check --as-cran`, failing on warnings, on Linux, macOS, and Windows with R release, devel, and oldrel-1, and with R 4.4.0, the oldest version DESCRIPTION declares (DEC-081), on Linux and on Windows. The Windows R 4.4.0 job is the fixtures' platform: only there do the tests compare numbers with the committed fixtures (DEC-080); elsewhere they compare everything else and skip the numbers.
- `rewrite-reference.yaml`: the reference suite (`validation/run-reference.R`) with the committed fixtures on their platform, and on Linux, macOS, and Windows with fixtures that pprof 1.0.3, built on the runner (`dev/reference/setup_reference_library.R`), regenerates there into a scratch folder; it also reports how far pprof 1.0.3 itself moves on each platform. Every job also runs the Cox comparisons with both Cox fixture sets (`validation/run-cox-reference.R`, DEC-135) and the pprofR comparisons (`validation/run-pprofr-reference.R`, DEC-159), which `R CMD check` cannot run, since the full sets are not in the tarball.
- `rewrite-coverage.yaml` (R and C++ coverage, failing below 90% of R lines), `rewrite-lint.yaml` (`lintr::lint_package()`, failing on any lint), `rewrite-pkgdown.yaml` (builds the site and keeps it as an artifact; publishing it is the package owners' decision, and the site is no longer committed in `docs/`), `rewrite-sanitizers.yaml` (the C++ code under sanitizers), and `rewrite-bench.yaml` (benchmarks against pprof 1.0.3, on demand).
- Dispatched by hand: `cox-fixtures.yaml` (regenerates the Cox fixtures into an artifact, for a regeneration the project lead approves), `cox-bench.yaml` (the paired Cox benchmarks on a runner with 16 GB of memory), and `rhub.yaml` (R-hub's platforms, such as CRAN's check without long doubles).

Every job copies its results into GitHub annotations (`.github/scripts/ci-annotate.R`): the failing sections of the check log, each failing test with the first line of its message, a replay of a failed installation of the dependencies, the reference suite's summary and the fixture differences, and the platform (R, OS, BLAS, LAPACK, compiler). The public GitHub API returns annotations without signing in, which the logs and artifacts need: `Rscript dev/tools/ci_runs.R <output file> <run id> ...` reads them. The failures CI found during the rewrite, with their causes and fixes, are in the history (`dev/design/phase8-facts/08_ci_diagnosis.md`, `dev/README.md`).
