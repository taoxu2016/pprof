# Benchmarks at the Phase 4 gate (2026-10-03)

The working tree against the Phase 1 baseline (`reference-baseline-20261002-windows.csv`, DEC-023), on the baseline's machine: Windows 11 x64 (build 22621), Intel family 6 model 140, 8 cores, 7.4 GB of memory, R 4.4.0, one thread.

## Summary

- `linear_fe()` is about 50 times faster than the reference's, with half the peak memory or less: 0.077 s against 3.25 s on 1e5 observations of 1,000 providers (397 MB against 801 MB), and 1.99 s against 95.9 s on 1e6 observations of 100,000 providers (609 MB against 1291 MB). It demeans within providers instead of building dense centering matrices (DEC-006).
- `logis_firth()` is 12% to 40% faster than the baseline, and 40% to 45% faster than the reference measured alternately at 1e5 and 1e6 observations (paired median ratios 0.51 to 0.60); at 1e4 the two rounds disagree (1.32 and 0.70, a difference of 0.015 s). Its peak memory at 1e6 is 674 MB against 750 to 759 MB. The engines alone run at the same speed (below); the gain is in the R code around them.
- The RE and CRE fits take the reference's time: paired ratios between 0.91 and 1.03; they make the reference's lme4 calls (DEC-042).
- No task regresses in time, in the comparison or in the paired re-measurement.
- Every flag is peak memory, from two causes: a transient of about 60 MB while pprof's dependencies load, and the process peak of `logis_fe` with 50 covariates on 1e6 observations, which the Phase 3 tree already had. Both are exceptions, accepted as recommended with the gate approval (2026-10-04, DEC-044).

## Peak memory

### The dependencies' load order

The comparison flags 30 tasks and the paired re-measurement 6 for peak memory 50 to 70 MB (12% to 22%) above the reference's, every one of them on 1e4 or 1e5 observations, where the peak of the process is set while the package loads, before the task runs. Measured in fresh processes set up as the harness sets them up:

| Install | Peak after `library(pprof)` | Memory in use after it |
|---|---|---|
| Reference (pprof 1.0.3) | 294 MB | |
| Phase 3 gate tree (`c430436`) | 294 MB | 289 MB |
| Phase 4 tree | 357 MB | 288 MB |
| Phase 4 tree, Matrix loaded before its imports | 295 MB | |

The memory in use after loading is the same; the difference is a transient. Phase 4 removed `importFrom(Matrix, bdiag)` with Matrix (DEC-009). That import was the first in NAMESPACE's alphabetical order, so Matrix used to load before caret; now caret loads first, and its loading raises the peak by 254 MB instead of 97 MB. Loading Matrix first brings the peak back to 294 MB, with the import order of either tree. The rewritten code is not involved: the namespace's own objects are the same size in both trees (21 MB by `object.size()`), and loading the namespace after its dependencies adds under 2 MB in both.

The transient goes when caret leaves Imports (DEC-009, with `check_data()`), or now if Matrix is imported again as the first import. The project lead decides; this report recommends leaving it to DEC-009, because it changes no result, affects only the moment pprof loads, and adding Matrix back would only work around caret.

### `logis_fe` with 50 covariates on 1e6 observations

| Measurement | Reference | Phase 3 gate tree | Phase 4 tree |
|---|---|---|---|
| Comparison run (process peak) | 2102 MB (baseline) | 2041 MB (Phase 3 gate) | 2567 MB |
| Paired rounds (process peak) | 2070, 2426 MB | | 2720, 2717 MB |
| Alternating fresh processes (process peak) | 2421, 2421 MB | 2557, 2675 MB | 2724, 2724 MB |
| Same processes, R's peak heap (`gc()` "max used") | 2217 MB | 2257 MB | 2257 MB |

Phase 4 did not change this path's memory: R's peak heap is the same for the Phase 3 and Phase 4 trees, 40 MB (1.8%) above the reference's, and the result object is the same size (554 MB). The process peak, measured as the benchmark measures it, varies by up to 360 MB between runs of the same code, and the Phase 3 tree measured now peaks at 2557 to 2675 MB, above its single gate measurement of 2041 MB. The Phase 4 tree's peak includes the 58 MB transient above. The rest of the gap to the reference lies outside R's heap: C++ temporaries of the logistic FE engine and variance routine, or the allocator. This report proposes to investigate it with the logistic FE work of Phase 5 or with the hardening of Phase 8; it is recorded as an exception until then.

## The first run of the gate

The first run, at `0ea7ab8`, measured a debug build: `R CMD INSTALL` on the source directory reused the objects in `src/` ("make: Nothing to be done for 'all'"), which `devtools::load_all()` had compiled with `-g -O0`, so the installed DLL was 16.5 MB against the reference's 1.5 MB. Its time measurements are not valid for the working tree. Commit `2f4556b` makes the harness install with `--preclean`, which recompiles every object with R's release flags (checked: 14 objects at `-O2`, a 1.48 MB DLL). That commit's message implies that the debug build also caused the 60 MB memory flags; the release run disproved this (the cause is the load order above).

## The Firth engine (Phase 4 step 1)

At step 1 an engine-level comparison found the new engine 45% to 50% slower than the reference's `logis_firth_prov()`. Both engines were then in the package as `devtools::load_all()` compiles it, with `-g -O0`, where the new engine's small per-provider functions and Armadillo expressions are not inlined. Compiled as release builds and timed alternately in fresh processes on the three Firth scenarios, the engines take the same time:

| Scenario | Reference median s (rounds 1, 2) | New median s | Reference fastest s | New fastest s |
|---|---|---|---|---|
| bin-1e4-m100-p5 | 0.0141, 0.0143 | 0.0142, 0.0142 | 0.0139, 0.0139 | 0.0139, 0.0139 |
| bin-1e5-m1000-p5 | 0.1440, 0.1451 | 0.1444, 0.1460 | 0.1432, 0.1438 | 0.1439, 0.1429 |
| bin-1e6-m1000-p5 | 1.371, 1.293 | 1.309, 1.372 | 1.168, 1.170 | 1.172, 1.176 |

Both engines return the same estimates (the first coefficient agrees to every digit printed in every run).
